# 开发者工作流

> **大部分已落地**：无限制覆盖（§1）、扫描与打包（§3）、开发者工作台（§4）都能用了，
> 入口是启动器的「开发者页」；落点规则见 [`package-format.md`](./package-format.md) §1.9。
> **只有版本管理还缺** —— 现在只记路径 + 大小 + 修改时间，内容级 diff 要接 SC2Diff，
> 所以在界面上暂时藏起来了（`SHOW_VERSION_CONTROL`）。
> 目标不变：让作者**在游戏目录里直接开发**，做出来的东西和玩家装的是**同一种格式**。

## 0. 四个子系统

| # | 子系统 | 解决什么 |
| --- | --- | --- |
| 1 | **无限制覆盖** | 包想装到哪就装到哪，不牺牲开发自由度 |
| 2 | **快照与还原** | 上一条的安全网：被动过的文件都能原样回来 |
| 3 | **扫描与声明（MY 包）** | 把"现在装在我游戏里的这些东西"变成一个包 |
| 4 | **开发者工作台** | 看变化、提交版本、对比、只导出差异 |

---

## 1. 无限制覆盖

**决策：落点不再限制在 `Maps` / `Mods` / `Interfaces` 之内。**

- `to` 可以指向游戏目录里的任何位置（`SC2Data/`、游戏根、`Versions/` …）
- 入口名里的 `..` 仍然拒绝 —— 它在 `from` 内部没有意义，只会是打包打错了
- 符号链接（tar 能带）仍然不做，但**理由不是安全**：备份与还原对它没有意义
  （记的是链接还是目标？还原时目标还在不在？）见 §7

代价必须写在明面上：**包因此有能力覆盖游戏本体、覆盖启动器自己、覆盖用户文档。**
安全网只有一条 —— 第 2 节的快照，所以快照是**强制**的，不是可选项。

唯一保留的闸门是**知情同意**，不是禁止：导入时把变更清单摆出来，
落在游戏目录之外的路径单独标红，勾一下才继续。

## 2. 快照与还原

### 2.1 铺盘前：预演

`Plan` 先算成一份 `PreviewPlan`，**不写盘**，四类：

| 类别 | 含义 |
| --- | --- |
| `add` | 新增（目标原本不存在） |
| `overwrite` | 覆盖（目标存在且内容不同）→ **要备份** |
| `skip` | 目标已存在且内容一样 → 不动 |
| `delete` | 我们上次装的、这次不要了 → **要备份** |

界面上一行摘要：`+12 ~3 -1 · 340 MB`。**这就是导入确认框的主体内容**，
而不是一句"确定要装吗"。

### 2.2 铺盘时：快照

任何 `overwrite` / `delete` 的目标，动它之前先落一份快照：

```text
data/snapshots/<时间戳>-<短id>/
├── index.json          # 每条：原始绝对路径、大小、SHA-256、是不是目录、来源 owner
└── files/<编号>        # 原文件
```

- **硬链接优先**：同一个卷上零拷贝，几 GB 的地图也是瞬间完成。前提是落盘一律
  **替换**而不是原地改（见 2.4）
- 跨卷 / 文件系统不支持硬链接 → 退回复制
- 只快照**会被动到的**文件，不是整个游戏目录（那是几十 GB）
- 快照不自动清理；界面上看得到每个快照多大、什么时候的，自己删

### 2.3 还原

「还原到这个快照」= 删掉快照之后新增的 → 把快照里的文件放回原位 → 恢复被删的 →
逐条校验 SHA-256，对不上的**列出来**（见 2.5）。

界面上是一个按钮，不是一个命令 —— 出事的时候用户没心情敲命令。

### 2.4 绝不原地改

落盘一律「写临时文件 → rename 替换」，**不在已存在的目标文件上原地写**。

两个理由：硬链接快照只有在替换语义下才安全（原地写会同时改掉备份）；
原地写一半失败就是半个文件。

> 现有 `install.rs::copy_entry` 是"复制到目标"，要确认它在目标已存在时是替换
> 而不是覆写同一个句柄 —— 这是 P0 的第一件事。

### 2.5 为什么不做常驻文件监控

"文件监控系统"有两种做法：

| 做法 | 代价 |
| --- | --- |
| 常驻 watcher（`notify` crate）盯着游戏目录 | 多一个依赖；SC2 一局游戏能写几千个文件；要处理自指写入；启动器没跑时漏事件 |
| **台账 + 还原前重校验**（推荐） | 零依赖；只在需要时算 |

**已定：按后者做，而且监控范围只到「本次会覆盖的内容」** —— 就是预演算出来的
`overwrite` / `delete` 那一批，动它们之前逐个备份。别的文件一个都不碰。

第一次实现**不做常驻 watcher**。真需要「游戏里改完立刻看见」时再补，
那时也做成**按需扫描**（点一下刷新）而不是守护进程。

## 3. 扫描与 MY 包

### 3.1 扫什么

`Installation` 已经给出全部根，不用新发现逻辑：

```text
<游戏>/Maps/                    <游戏>/Maps/Campaign/
<游戏>/Maps/CustomCampaigns/    <游戏>/Mods/          <游戏>/Interfaces/
<文档>/StarCraft II/Maps/       （用户自己的图）
```

扫出来的是一棵**可勾选的树**，每个节点带：体积、修改时间、
`我们装的?`（查台账）、`被改过?`（比对台账里的 SHA-256 —— **这就是"开发中"的信号**）。

### 3.2 声明为 MY 包

勾选 → 填 名字 / 作者 / 版本 / 归属 → 生成 `data/projects/<id>/project.json`：

```json
{
  "name": "复刻战役",
  "author": "某人",
  "version": "8.0",
  "campaign": "custom",
  "mode": "linked",
  "overrides": [
    { "from": "Maps/CustomCampaigns/Starcraft Mass Recall", "to": "Maps/Starcraft Mass Recall" },
    { "from": "Mods/SCMRmod.SC2Mod", "to": "Mods/SCMRmod.SC2Mod" }
  ]
}
```

**`mode: linked` 是这个功能的关键**：不复制内容，直接引用游戏目录里现有的文件。

- 开发者在游戏目录里改地图 → 启动器一扫就看见
- **提交成版本时**才去读文件内容
- `mode: archived` 是传统的"内容在库里"，两种状态可以互转
  （「收进库里」/「放回游戏目录」）

这样"一边开发一边管理"才成立：开发者不需要理解库的目录结构，
游戏目录就是他的工作区。

### 3.3 快捷打包

「打包」= 按 `overrides` 把勾选的文件收进 zip：

```text
复刻战役-8.1.zip
├── metadata.txt          # CCM 能读的那份
├── Miyin/metadata.json   # 完整声明
└── Miyin/overrides/…     # 覆盖内容
```

打包是一次**投影**：同一份 `project.json`，可以打出「CCM 能读的部分」和「完整包」两种。

## 4. 开发者工作台（界面设计）

### 4.1 位置

顶栏加一个标签**「开发」**，与「战役 / 自制战役 / 模组 / 设置」并列。

**没装 SC2Diff 也进得去** —— 只有"语义 diff"那一栏显示"未装 SC2Diff"，
而不是整页禁用。扫描、声明、打包、快照都不依赖它。

### 4.2 三栏

```text
┌─ 开发 ─────────────────────────────────────────────────────────────┐
│ [包]  复刻战役 ▾    基线 v8.0     ● 3 处未提交                      │
├────────────────┬────────────────────────┬─────────────────────────┤
│ 游戏目录        │ 相对基线的变化          │ 语义 diff                │
│ ▸ Maps/        │                        │                         │
│  ▸ Custom…     │ ~ Terran01.SC2Map 改动  │ 单位 Marine              │
│   ▸ 1. Rebel…  │ + Epilogue.SC2Map 新增  │   生命  45 → 60          │
│   ▸ Mods/      │ - Old.SC2Mod     删除   │   武器  Gauss → Impaler  │
│ ▸ Interfaces/  │                        │                         │
│                │ 12 项 · 340 MB          │ ▸ Terran01.SC2Map        │
│ [全选][反选]    │ [预览] [提交为 v8.1]    │ ▸ Epilogue.SC2Map（无差异）│
├────────────────┴────────────────────────┴─────────────────────────┤
│ 版本：v8.0  ●── v8.0.1  ●── v8.1（未提交）    [对比] [回滚] [导出]   │
└───────────────────────────────────────────────────────────────────┘
```

- **左栏**：扫描出来的游戏目录，勾选即纳入这个包。改过的行左边有个点
- **中栏**：相对**基线版本**的变化，底部两个按钮 —— 预览（dry-run）与提交
- **右栏**：语义 diff（内置 SC2Diff），点一行看具体改了什么
- **底栏**：版本链，点两下选两个版本对比

### 4.3 版本管理（基于内置 SC2Diff）

| 功能 | 做法 |
| --- | --- |
| 版本列表 | SC2Diff 的提交链（第一父链够了，不做分支） |
| 每版信息 | 提交信息、时间、文件数、体积、**相对上一版的净增体积** |
| 对比任意两版 | 文件级 + 语义 diff（现有 `mods::compare` 的形状直接复用） |
| 回滚 | **新提交一次 revert**，不改写历史 —— 历史是开发者的记忆，不能消失 |
| 导出 | 默认建议 `bundle --basis`（只带差异），并在按钮上写明"完整 961 KB / 仅差异 8.2 KB" |

**存储分两块**，各用各的：

| 内容 | 后端 |
| --- | --- |
| 载荷文档（`.SC2Map` / `.SC2Mod`） | **每份文档一个 SC2Diff 仓库** —— 它擅长的就是文档版本与语义 diff，`bundle --basis` 直接给出 issue #16 要的"只存差异" |
| 其余文件（`.dds`、`.xml`、脚本…） | 我们自己的内容寻址：按 SHA-256 存一份，版本只记路径 → 哈希（约 20 行） |

两边的版本号对齐（同一个提交名），界面上当一件事看。

> 不把整个项目塞进**一个** SC2Diff 仓库：它处理的是"一份文档"，
> 让它管一堆散文件是硬套，将来出问题也不好查。

### 4.4 SC2Diff：内置固定版本 + 静默更新

现在是**下载**的（`tools/mod.rs`，装在 `<data>/tools/sc2diff/`），而且那次下载**不校验摘要**。
SC2Diff 是我们自己的项目（`SuperQuail/SC2Diff`），会持续更新 —— 所以既不改成纯下载，
也不冻在里面：

**内置一个固定版本，后台静默更新。**

- 随包带一个固定版本（Tauri resources 或 exe 同级 `tools/`），**首次启动不联网也能用**
- 启动后（或每天一次）后台查一次新版本，**静默换掉** `data/tools/sc2diff/` 里那份
- 换的时候**校验 SHA-256**：Release 有摘要就用摘要，没有就**跳过这次更新**而不是盲装
- 界面只在「设置 → 可选工具」里显示当前版本与「上次更新于」，不弹窗、不打断
- 网络挂了、被墙了、Release 下架了，内置那份还在 —— 用户始终能用

体积代价约 1.4 MB（当前发行包 7 MB），换来的是**离线可用且可更新**，而不是二选一。

### 4.5 界面上怎么体现"智能"

不是加一个"AI"标签，而是**把作者本来要自己判断的事算出来**：

- 变更清单里区分三类：**语义有变化**（SC2Diff 说改了东西）/ **只是重新保存**
  （字节变了但语义一样）/ **完全没变**
- 版本卡上显示**净增体积**："这一版只有 8 KB 是新的"
- 导出时默认选"只带差异"，并写明省了多少

## 5. 分阶段

| 阶段 | 内容 | 验收（能手动跑通） |
| --- | --- | --- |
| **P0** | 无限制覆盖 + 快照 / 还原 + 预演确认框 | 覆盖官方文件后一键完全还原；强杀启动器后快照仍可用 |
| **P1** | 扫描 + 声明 MY 包 + 打包 | 把已装的复刻战役声明成包，打出 zip，另一台机器导入后一致 |
| **P2** | 内置 SC2Diff + 版本列表 + 对比 / 回滚 | 改一张图 → 看见语义 diff → 提交 v8.1 → 回滚到 v8.0 |
| **P3** | 工作台整合 + 只导出差异 | 一个版本只带 8 KB 差异，对方导入后与完整包一致 |

每阶段能独立发布、独立验收。P0 是其余全部的前提 —— 没有可还原的快照，
后面每一阶段都在赌用户的数据。
